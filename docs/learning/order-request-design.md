
# 주문 요청 설계

주문 API에서 클라이언트 입력을 어떻게 검증하고, 거래 가격을 어떤 기준으로 확정하며, 요청자의 접근 권한을 어떻게 확인할지 정리한다.

**구현 상태:** 1절의 요청 구조, 2절의 입력값·업무 규칙 검증, 3절의 가격 재확인 정책, 4절의 가격 스냅샷은 주문 생성 API(`POST /api/v1/orders`)에 구현되었다. 2절의 인증·인가와 3절의 가격 보장(대안)은 구현하지 않았다. 요청·응답 형식의 기준은 OpenAPI 명세(`server/openapi/customer.json`)다.

## 1. 요청 데이터와 신뢰 경계

주문 요청에는 클라이언트가 선택하는 정보와 서버가 확인하거나 생성해야 하는 정보가 함께 존재한다.

두 정보를 구분하지 않으면 가격 조작, 타인 명의의 주문 생성, 잘못된 데이터 저장 등의 문제가 발생할 수 있다.

| 정보 | 출처 및 처리 원칙 |
| --- | --- |
| 상품 ID·수량 | 클라이언트가 선택하며 서버에서 유효성을 검증 |
| 고객이 확인한 총액 | 클라이언트가 전달하며 서버 계산 결과와 비교 |
| 상품 단가 | 서버의 가격 정책에 따라 조회·확정 |
| 주문 고객 ID | 검증된 인증 정보에서 확인 |
| 주문 번호·주문 시각 | 서버에서 생성 |
| 배송지·결제수단 | 소유권과 사용 권한을 검증하는 정책 필요 |
| 배송 요청사항 | 입력 형식과 허용 범위 검증 필요 |

요청은 다음 필드로 구현했다.

- `customerId`: 주문 고객 식별자. 인증이 없어 임시로 요청에서 받는다
- `lines[]`: 주문 항목. 각 항목은 `productId`(상품 식별자)와 `quantity`(주문 수량). 같은 상품은 한 항목에만 둔다
- `expectedTotal`: 고객이 주문 전 확인한 총액. `{"amount": "15000", "currency": "KRW"}`

상품 식별자는 [ADR-0001](../decisions/0001-entity-identifiers.md)에 따라 `java.util.UUID`를 사용한다.

수량은 1 이상의 정수다. 금액은 문자열 소수(`amount`)와 ISO 4217 통화 코드(`currency`)로 주고받는다. 통화의 소수 자릿수보다 소수가 많은 입력 금액은 반올림하지 않고 거절하며, 서버가 계산한 금액은 통화 자릿수로 정규화(HALF_UP)한다.

## 2. 요청 검증

주문 요청에 필요한 검증은 목적에 따라 구분한다.

| 구분 | 검증 내용 |
| --- | --- |
| 입력값 검증 | UUID 형식, 필수 항목, 수량·금액의 허용 범위 |
| 업무 규칙 검증 | 상품 존재 여부, 판매 상태, 가격·할인 조건 |
| 인증(Authentication) | 요청자의 신원 확인 |
| 인가(Authorization) | 요청자가 해당 자원에 접근하거나 작업할 권한이 있는지 확인 |

입력값이 유효하다는 사실만으로 업무 요청이 허용되는 것은 아니다.

예를 들어 고객 A의 Bearer 토큰을 정상적으로 검증했더라도, 고객 B의 주문을 조회하거나 변경할 권한이 있는지는 별도로 확인해야 한다.

## 3. 가격 검증과 주문 확정

클라이언트가 전달한 금액은 신뢰할 수 있는 가격 정보가 아니라, **고객이 확인한 금액을 나타내는 입력값**으로 취급한다.

주문에 적용할 금액은 서버가 상품 가격과 주문 조건을 검증하여 계산한다.

### 가격 변경 시나리오

고객이 상품 3개를 개당 5,000원에 선택하여 총 15,000원을 확인했으나, 주문 요청 시점의 서버 기준 단가가 6,000원으로 변경된 상황을 가정한다.

1. 서버가 상품 가격과 수량을 바탕으로 총액 18,000원을 계산한다.
2. 요청에 포함된 `expectedTotal`과 비교한다.
3. 금액이 다르면 주문 확정을 중단하고 변경된 금액을 안내한다. 구현에서는 409 `TOTAL_MISMATCH`와 현재 총액(`currentTotal`)을 응답한다.
4. 고객이 변경된 금액을 확인하고 다시 요청하면 서버가 가격 및 주문 조건을 재검증한다.
5. 검증에 통과하면 최종 적용한 가격을 주문에 저장한다.

이 방식은 **주문 요청 시점에 서버 기준 가격을 재확인하는 정책**이다. 가격이 여러 처리 단계에서 변경될 가능성과 가격 확정 시점의 일관성도 구현 과정에서 검토해야 한다.

### 대안: 가격 보장

서버가 견적을 생성하고 일정 시간 동안 가격을 보장하는 방식도 가능하다.

다만 견적의 유효기간, 수량 변경, 할인 조건 변경 및 만료 처리 등의 정책이 추가로 필요하다.

현재는 주문 요청 시점에 재확인하는 방식을 구현했다. 가격 보장은 검토만 했으며 구현하지 않았다.

## 4. 주문 가격 보존

상품의 현재 판매 가격과 과거 주문에 실제 적용된 가격은 구분해야 한다.

예를 들어 상품 3개를 개당 5,000원에 구매했다면, 이후 상품 가격이 6,000원으로 변경되더라도 해당 주문의 거래 금액은 15,000원으로 유지되어야 한다.

이를 위해 주문 항목에 주문 당시 적용한 단가와 수량을 저장한다. 구현에서는 상품명도 함께 저장한다(`order_line`).

이처럼 특정 시점에 확정된 정보를 별도로 보존하는 방식을 스냅샷(Snapshot)이라고 한다.

주문 가격 스냅샷은 상품 정보의 변경과 관계없이 과거 거래를 조회하고, 취소·환불 등의 후속 처리를 수행하기 위한 기준이 된다.

할인, 세금, 배송비 등 추가 금액 요소의 보존 범위는 주문 모델을 구체화할 때 결정한다.

## 5. 식별자 정책

식별자의 생성 방식, 애플리케이션 타입, 데이터베이스 저장 방식 및 API 표현은 서로 구분한다.

예를 들어 UUID를 API에서 문자열로 전달하더라도 애플리케이션에서는 `java.util.UUID`, PostgreSQL에서는 네이티브 `uuid` 타입으로 처리할 수 있다.

또한 Java의 `UUID` 타입은 UUIDv7만 허용하는 타입이 아니다. UUID 버전 제한이 필요한 경우에는 별도의 검증 정책을 정의해야 한다.

식별자 형식 검증, DB 유일성 제약, 자원 존재 여부 및 접근 권한 확인은 각각 다른 책임이다.

ID 생성 전략과 분산 환경에서의 유일성 보장 방식은 [ADR-0001](../decisions/0001-entity-identifiers.md)에서 관리한다.


# ADR-0001: 엔티티 식별자에 UUIDv7 사용

| 항목 | 내용 |
| --- | --- |
| 상태 | 채택 |
| 결정일 | 2026-11-01 |
| 적용 범위 | 상품·주문·결제 등 주요 엔티티의 신규 식별자 |
| 구현 상태 | 애플리케이션 미적용 |
| 검증 상태 | 로컬 생성·저장 검증 및 PostgreSQL 인덱스 비용 비교 완료 |

## 요약

- **결정:** 주요 엔티티의 식별자로 UUIDv7을 사용한다. (Hibernate `VERSION_7`, PostgreSQL 네이티브 `uuid`)
- **이유:** 머신 ID 관리 없이 각 애플리케이션 인스턴스가 독립적으로 ID를 발급할 수 있다.
- **비용:** 100만 행 로컬 실험에서 PK 인덱스가 BIGINT 대비 약 40~49% 컸고, 도착 순서를 섞은 조건에서는 UUIDv4보다도 컸다.
- **재검토:** 누적 저장 비용이나 쓰기 성능이 문제가 되면 DB 시퀀스, Snowflake 등 BIGINT 계열 대안과 다시 비교한다.

## 1. 배경

Etude는 여러 애플리케이션 인스턴스가 독립적으로 동작하는 분산 환경을 설계 목표로 한다.

상품·주문·재고·결제 등 여러 도메인에서 식별자를 공유하거나 참조해야 하므로, 다음 요구사항을 고려한다.

- **독립 발급:** 여러 애플리케이션 인스턴스가 별도의 중앙 채번 요청 없이 ID를 생성할 수 있어야 한다.
- **유일성:** 인스턴스 확장·재시작·재배포 상황에서도 식별자 충돌 위험을 충분히 낮춰야 한다.
- **저장 효율:** 식별자의 크기와 생성 순서가 PostgreSQL 인덱스 및 조회 성능에 미치는 영향을 고려한다.
- **도메인 간 참조:** 상품 도메인에서 발급한 식별자를 다른 도메인에서도 동일하게 사용할 수 있어야 한다.
- **보안:** 외부에 노출된 식별자가 접근 권한을 대신하지 않도록 설계한다.

상품 조회가 등록보다 빈번할 것으로 예상하지만, 실제 읽기·쓰기 비율은 측정하지 않았다.

또한 상품 등록, 가격 변경, 재고 갱신은 서로 다른 작업이므로 식별자 생성 빈도와 데이터 변경 빈도를 구분한다.

## 2. 결정

주요 엔티티의 식별자 생성 방식으로 **UUIDv7을 채택한다.**

| 구분 | 결정 |
| --- | --- |
| 생성 주체 | 애플리케이션의 Hibernate UUID 생성기 |
| 생성 방식 | `UuidGenerator.Style.VERSION_7` 명시 |
| Kotlin 타입 | `java.util.UUID` |
| PostgreSQL 타입 | 네이티브 `uuid` 및 `PRIMARY KEY` |
| API·이벤트 표현 | 표준 UUID 문자열 |
| 도메인 간 참조 | 원천 도메인에서 발급한 식별자를 그대로 사용 |

Hibernate 7.4에서는 `AUTO`가 `RANDOM`(UUIDv4)을 기본으로 선택하므로 UUIDv7을 명시적으로 지정한다.

상품·주문·결제 등 주요 엔티티에는 동일한 생성 정책을 기본 적용한다. 단, 연결 테이블의 복합 키처럼 별도 설계가 적합한 경우에는 데이터 모델의 특성을 우선한다.

다른 식별자 체계가 필요한 경우에는 요구사항과 검증 결과를 별도 ADR로 기록한다.

## 3. 선택 근거

### 3.1. 독립적인 ID 생성

UUIDv7은 타임스탬프와 난수 기반 구성 요소를 활용해 식별자를 생성한다.

별도의 머신 ID를 할당하지 않고 여러 애플리케이션 인스턴스에서 독립적으로 발급할 수 있다는 점을 주요 장점으로 판단했다.

Snowflake도 분산 발급이 가능하지만, 발급기마다 구분 가능한 머신 ID를 관리해야 한다.

특히 Kubernetes 환경에서는 Pod의 확장·재시작·재배포에 따라 발급기 구성이 달라질 수 있으므로 머신 ID의 할당, 중복 방지 및 재사용 정책이 필요하다.

단, Snowflake에 중앙 발급 서버가 반드시 필요한 것은 아니다. 이러한 운영 관리 비용이 UUID의 추가 저장 비용보다 크다는 점도 정량적으로 검증하지 않았다.

UUIDv7 역시 충돌 가능성이 완전히 제거되는 것은 아니며, 최종적으로 데이터베이스의 유일성 제약을 유지한다.

### 3.2. 시간순 특성과 인덱스 지역성

UUIDv7은 상위 48비트에 Unix 밀리초 타임스탬프를 포함한다.

따라서 생성 시각이 가까운 식별자들이 B-tree 인덱스에서도 가까운 위치에 배치될 가능성이 있다.

이는 UUIDv4처럼 무작위로 분포하는 키와 비교했을 때 삽입 지역성을 개선할 수 있는 특성이다.

다만 실제 인덱스 크기와 성능은 다음 조건의 영향을 받는다.

- 여러 인스턴스에서 생성된 ID의 도착 순서
- 동일한 시간 구간에서 생성된 ID의 정렬 특성
- 데이터 삽입 및 갱신 패턴
- 인덱스 페이지 분할과 내부 공간 활용률

따라서 UUIDv7이 항상 UUIDv4보다 작은 인덱스나 높은 성능을 제공한다고 가정하지 않는다.

### 3.3. 저장 공간 비용

UUID는 128비트(16바이트)로, 64비트(8바이트)인 `BIGINT`보다 크다.

이 차이는 PK 인덱스뿐 아니라 해당 ID를 저장하는 외래 키, 관련 인덱스 및 데이터 전송량에도 영향을 줄 수 있다.

PostgreSQL은 테이블의 heap과 각 인덱스를 별도로 관리한다. 따라서 PK 크기의 차이가 모든 보조 인덱스 크기에 동일한 비율로 반영되는 것은 아니다.

저장 비용은 수용하되, 실제 차이는 로컬 실험으로 비교한다.

### 3.4. 기술 지원과 운영 특성

현재 검증에 사용한 Hibernate 7.4.13.Final은 UUIDv7 생성 전략을 지원한다.

다만 `VERSION_7`은 `@Incubating` API로 표시되어 있으므로, Hibernate 버전 업그레이드 시 생성 방식과 호환성을 재검증한다.

또한 UUIDv7에는 생성 시각이 포함되지만, 여러 서버에서 생성한 ID의 전역적인 순서를 보장하지 않는다.

주문 처리 순서나 이벤트 발생 순서처럼 업무상 정확한 순서가 필요한 경우에는 별도의 순서 보장 정책을 설계한다.

## 4. 검토한 대안

| 대안 | 장점 | 선택하지 않은 이유 |
| --- | --- | --- |
| BIGINT + DB 시퀀스 | 작은 키 크기, DB의 동시 발급 관리 | 공유 시퀀스를 사용하는 방식은 유효하지만, 이번에는 애플리케이션의 독립 발급을 우선 |
| Snowflake | 작은 정수 키, 시간순 특성, 분산 발급 | 머신 ID의 유일성·재사용, 시계 및 시퀀스 관리 필요 |
| UUIDv4 | 독립 발급 가능, 생성 시각을 구조에 포함하지 않음 | 무작위 삽입에 따른 인덱스 비용을 고려하여 v7 선택 |
| 내부 BIGINT + 외부 UUID | 내부 저장 효율과 외부 식별자 분리 가능 | 별도 식별자 매핑, 유일성 제약 및 추가 인덱스 관리 필요 |

DB 시퀀스는 여러 애플리케이션 서버가 하나의 데이터베이스를 공유하는 환경에서 충분히 유효한 선택이다.

Snowflake 또한 적절한 머신 ID 관리 체계를 갖추면 중앙 발급 서버 없이 사용할 수 있다.

따라서 UUIDv7 선택은 다른 방식이 기술적으로 부적합하기 때문이 아니라, **현재 설계에서 독립 발급과 운영 관리의 단순성을 우선한 결과**다.

## 5. 보안 고려사항

난수 기반 구성 요소를 포함하는 UUID는 순차적인 정수 ID보다 식별자 추측과 열거를 어렵게 만들 수 있다.

하지만 UUIDv7에는 생성 시각이 포함되며, 추측 난도는 생성기의 난수 품질과 구현 방식에 영향을 받는다.

또한 공개 상품 목록처럼 식별자가 이미 노출되는 환경에서는 이러한 효과가 제한적이다.

따라서 식별자의 예측 가능성과 접근 권한은 별개의 문제로 취급한다.

- 인증된 사용자인지 확인한다.
- 요청자가 해당 자원에 접근할 권한이 있는지 검사한다.
- 상품 조회와 개인 주문 조회 등 자원별 접근 정책을 구분한다.
- 식별자를 알고 있다는 사실을 소유권이나 접근 권한의 증거로 사용하지 않는다.
- 데이터베이스의 PK·유일성 제약을 유지한다.

**UUID 사용은 인증·인가를 대체하지 않는다.**

## 6. 로컬 검증

### 6.1. 실험 환경

2026-11-01 기준 로컬 환경에서 검증했다.

| 항목 | 환경 |
| --- | --- |
| OS | Windows |
| CPU | AMD Ryzen 5 7500F |
| RAM | 약 32 GiB |
| PostgreSQL | 18.4 |
| Java | 25 |
| Kotlin | 2.3.21 |
| Hibernate | 7.4.13.Final |
| JDBC Driver | 42.7.14 |

검증은 생성 정확성, 데이터베이스 저장·조회, 키 유형별 인덱스 비용을 중심으로 수행했다.

### 6.2. 생성 및 저장 검증

| 검증 항목 | 결과 |
| --- | --- |
| Hibernate 엔티티 ID 생성 | UUID version=7, variant=2 확인 |
| Kotlin·JSON·JDBC·DB 왕복 | 저장·조회 값 일치, 잘못된 UUID 문자열 거부 |
| 중복 PK 삽입 | SQLSTATE `23505`로 거부 |
| 8개 스레드에서 160,000개 생성 | 검사 집합 내 중복 미발견 |
| JVM 3개를 두 차례 시작해 총 300,000개 생성 | 검사 집합 내 중복 미발견 |
| 마지막 생성 시각을 60초 미래로 주입한 뒤 10,000개 생성 | 해당 생성기 내 증가 확인 |

검사 결과는 사용한 생성기가 해당 조건에서 정상 동작했음을 보여준다.

그러나 중복이 발견되지 않았다는 사실이 충돌 가능성이 0임을 증명하지는 않는다.

또한 JVM 재시작 검사는 정상 종료 후 새 JVM을 시작한 방식이며, 시계 역행 검사는 내부 상태 주입을 통한 모의 실험이다.

실제 OS 시계 변경, 비정상 종료 및 VM 복원 상황은 검증하지 않았다.

### 6.3. PostgreSQL 인덱스 비교

식별자 타입과 데이터 도착 순서에 따른 인덱스 비용을 비교했다.

**실험 조건**

- 후보별 테이블에 100만 행 삽입
- 8개 클라이언트 사용
- 후보별 3회 반복
- 생성 순서 유지 및 1,024행 구간 내 도착 순서 섞기 비교
- UUIDv7은 4개 생성기를 번갈아 사용
- PK 인덱스 크기는 3회 측정값의 중앙값 사용

BIGINT 후보는 Snowflake 형태의 시간·worker·순번으로 구성한 데이터를 사용했다.

따라서 해당 실험은 BIGINT 키의 저장·조회 특성을 비교한 것이며, 실제 Snowflake 생성기의 성능과 운영 안정성을 검증한 것은 아니다.

또한 UUIDv7의 생성 순서 유지 조건은 여러 생성기 간 전역적인 완전 정렬을 의미하지 않는다.

#### PK 인덱스 크기

| 식별자 | 생성 순서 유지 | 1,024행 단위 섞기 |
| --- | ---: | ---: |
| Snowflake 형태 BIGINT | 21.45 MiB | 26.91 MiB |
| UUIDv4 | 37.70 MiB | 37.55 MiB |
| UUIDv7 | 30.00 MiB | 40.03 MiB |

**관찰 결과**

- 생성 순서를 유지한 조건에서 UUIDv7은 UUIDv4보다 작은 PK 인덱스를 사용했다.
- 1,024행 단위로 도착 순서를 섞었을 때 UUIDv7의 PK 인덱스가 UUIDv4보다 커졌다.
- UUIDv7은 BIGINT 대비 약 40~49% 큰 PK 인덱스를 사용했다.
- 인덱스 비용은 식별자 타입뿐 아니라 데이터 도착 순서에도 영향을 받았다.

#### 보조 인덱스

동일한 `(category, price)` 보조 인덱스의 크기는 모든 후보에서 중앙값 약 9.09 MiB였다.

이는 PostgreSQL의 보조 인덱스가 PK 값을 모든 엔트리에 자동으로 포함하는 구조가 아니기 때문이다.

다만 PK 크기가 heap의 행 크기와 ID를 포함하는 다른 인덱스에 미치는 영향은 별도로 고려해야 한다.

#### PK 조회 지연

아래 값은 조회 p95 측정치에 대해 3회 실행 결과의 중앙값을 구한 것이다.

단위는 ms다.

| 식별자 | 생성 순서 유지 | 1,024행 단위 섞기 |
| --- | ---: | ---: |
| Snowflake 형태 BIGINT | 0.0972 | 0.0949 |
| UUIDv4 | 0.1039 | 0.0987 |
| UUIDv7 | 0.0973 | 0.0985 |

조회 지연의 차이는 작은 수준이었다.

짧은 로컬 조회 실험이며 반복 횟수도 제한적이므로 특정 식별자 방식이 더 빠르다고 결론 내리지 않았다.

측정 중 체크포인트 및 혼합 쓰기 지연의 변동도 관찰되어, 장시간 부하 환경에서 추가 검증이 필요하다.

### 6.4. 검증 결과에 따른 판단

로컬 실험에서 다음 사항을 확인했다.

1. Hibernate의 UUIDv7 생성·저장·조회가 검증 조건에서 정상 동작했다.
2. 동시 및 다중 JVM 생성 검사에서 중복이 발견되지 않았다.
3. UUIDv7은 도착 순서에 따라 UUIDv4보다 인덱스 공간을 적게 또는 많이 사용할 수 있었다.
4. BIGINT는 실험한 조건에서 UUID보다 작은 PK 인덱스를 유지했다.
5. PK 조회 지연만으로는 식별자 방식 간 성능 우위를 판단하기 어려웠다.

따라서 UUIDv7의 저장 공간 비용과 성능상 한계를 인정하면서도, 현재는 독립 발급 시 머신 ID 조정 의존성을 줄이는 장점을 우선하기로 했다.

이는 현재 요구사항과 로컬 검증에 기반한 결정이며, 대규모 운영 환경에서 최적의 방식임을 입증한 것은 아니다.

## 7. 검증 한계

이번 검증은 단일 Windows 호스트에서 직접 JDBC를 사용하는 로컬 환경에 한정된다.

다음 항목은 검증하지 않았다.

- Spring HTTP 요청과 HikariCP를 포함한 전체 처리 경로
- Kubernetes·AWS·다중 AZ 환경에서의 동시 발급
- 장시간 부하 및 처리량 포화 지점
- 실제 OS 시계 역행, 비정상 종료, VM 복원
- 데이터 증가에 따른 인덱스 및 외래 키의 누적 저장 비용
- 운영 환경의 실제 데이터 도착 순서와 읽기·쓰기 비율
- OS 캐시 초기화 및 캐시 조건을 통제한 성능 비교

따라서 로컬 검증 결과를 실제 운영 환경의 RPS/TPS 처리 능력이나 지연 SLO 달성의 근거로 사용하지 않는다.

## 8. 재검토 조건

다음 상황에서는 UUIDv7 채택 여부를 다시 검토한다.

1. **데이터 규모 증가:** 예상 데이터 보유량과 메모리 예산을 기준으로 PK·외래 키·인덱스의 누적 저장 비용이 허용 범위를 초과하는 경우
2. **성능 목표 미달:** 목표 RPS/TPS 또는 지연 SLO를 충족하지 못하고 식별자 방식이 주요 병목으로 확인되는 경우
3. **실제 도착 패턴 변화:** 다중 인스턴스의 삽입 순서로 인해 인덱스 비용이나 쓰기 성능이 지속적으로 악화되는 경우
4. **생성 안정성 문제:** 시계 변화, 재시작 또는 높은 동시성 환경에서 생성기의 안정성 문제가 발견되는 경우
5. **라이브러리 변경:** Hibernate 업그레이드로 UUIDv7 생성 방식이나 API 호환성이 변경되는 경우

재검토 시에는 Snowflake, DB 시퀀스 또는 내부 BIGINT와 외부 UUID를 분리하는 방식을 대안으로 비교한다.

다만 식별자 변경은 기존 데이터, 외래 키, API 및 이벤트 계약에 영향을 주므로 실제 마이그레이션 비용도 함께 평가한다.

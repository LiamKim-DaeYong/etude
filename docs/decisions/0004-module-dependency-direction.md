# ADR-0004: 모듈 의존 방향과 주문 취소 이벤트 전달

| 항목 | 내용 |
| --- | --- |
| 상태 | 채택 |
| 결정일 | 2026-11-08 |
| 적용 범위 | 주문(`order`)과 재고(`inventory`) 모듈 사이의 호출과 이벤트, 주문 취소 시 예약 해제 |
| 구현 상태 | 주문 취소와 예약 해제에 적용(#93) |
| 검증 상태 | 모듈 순환·중복 취소·중복 전달을 재현하고 해결을 통합 테스트로 검증. 처리량과 이벤트 지연은 측정하지 않음 |

## 요약

- **결정:** 모듈 사이의 인터페이스는 **쓰는 쪽이 소유한다.** 주문이 재고에 요구하는 예약 포트(`InventoryReservation`)는 주문 모듈의 공개 패키지에 두고 재고 모듈이 구현한다. 재고 모듈은 주문 모듈의 `OrderCanceled` 이벤트를 받아 예약을 해제한다. 그래서 의존은 `inventory → order` 한 방향뿐이다.
- **전달:** 이벤트는 Spring Modulith의 이벤트 발행 기록(Event Publication Registry, JDBC)에 남기고, 주문 취소가 커밋된 뒤 별도 트랜잭션에서 비동기로 처리한다(`@ApplicationModuleListener`).
- **중복 방지:** 이벤트는 최소 한 번 전달된다. 재고 모듈은 주문별 예약 기록(`Reservation`)을 두고 예약됨 상태인 것만 해제하므로, 같은 이벤트가 다시 와도 재고가 두 번 늘지 않는다.
- **재검토:** 결제·만료·환불이 붙어 주문 모듈이 흐름 조율을 너무 많이 떠안으면, 주문·재고·결제 위에 흐름을 조율하는 모듈을 둔다.

## 1. 배경

주문할 때 주문 모듈은 재고 모듈의 `InventoryReservation`을 불러 재고를 예약한다(#84). 의존 방향은 `order → inventory`였다.

주문 취소(#93)는 예약한 재고를 되돌려야 한다. 이 단계의 목표는 Spring Modulith 이벤트로 모듈을 잇는 것이므로, 주문 모듈이 `OrderCanceled`를 발행하고 재고 모듈이 받게 했다. 그러자 재고 모듈이 주문 모듈의 이벤트 타입을 알아야 해서 `inventory → order` 의존이 생겼고, `ModularityTests`가 실패했다.

```
Cycle detected: Slice inventory -> Slice order -> Slice inventory
```

이벤트는 의존을 없애지 않는다. 받는 쪽이 이벤트 타입을 알아야 하므로 **의존 방향을 뒤집을 뿐이다.** 따라서 "어느 모듈이 어느 모듈을 알아야 하는가"를 정해야 했다.

고려한 조건은 다음과 같다.

- **예약은 즉시 답이 필요하다:** 주문할 때 재고가 부족하면 그 요청에서 409로 거절해야 한다. 예약은 동기 호출이어야 한다.
- **취소는 즉시 답이 필요 없다:** 재고 해제가 조금 늦어도 고객 응답에는 영향이 없다. 다만 해제가 빠지면 재고가 영영 묶이므로 유실되면 안 된다.
- **취소를 알고 싶은 모듈이 늘어난다:** 결제 환불, 알림 등이 이후 같은 사실을 받아야 한다.

## 2. 결정

1. `InventoryReservation`, `ReservationLine`, `InsufficientInventoryException`을 `com.etude.inventory`에서 `com.etude.order`로 옮긴다. 주문 모듈은 "재고가 이런 기능을 줘야 한다"를 정하고, 재고 모듈(`InventoryService`)이 구현한다. 주문 모듈은 재고 모듈을 전혀 참조하지 않는다.
2. 주문 모듈은 주문을 취소한 트랜잭션에서 `OrderCanceled(orderId)`를 발행한다. 이벤트는 발행한 모듈의 공개 패키지에 두고, 다른 모듈이 조회할 수 있는 식별자만 담는다.
3. 이벤트는 `spring-modulith-starter-jdbc`의 발행 기록(`event_publication` 테이블, 공식 v2 스키마)에 남긴다. 리스너는 `@ApplicationModuleListener`로, 발행 트랜잭션이 커밋된 뒤 새 트랜잭션에서 비동기로 실행된다. 리스너가 실패하면 기록이 `FAILED`로 남고 `IncompleteEventPublications`로 다시 제출할 수 있다.
4. 재고를 예약할 때 주문·상품마다 예약 기록(`reservation` 테이블, `(order_id, product_id)` 유일)을 남긴다. 이를 위해 주문 모듈은 주문을 먼저 저장해 ID를 받고 예약한다. 같은 트랜잭션이므로 예약이 실패하면 주문 저장도 롤백된다.
5. 예약 해제(`InventoryService.release(orderId)`)는 그 주문의 예약됨(`RESERVED`) 기록을 상품 ID 순으로 잠가 읽고, 기록마다 재고를 되돌린 뒤 해제됨(`RELEASED`)으로 바꾼다. 상품 ID 순 잠금은 ADR-0003의 규칙을 따른다.
6. 같은 주문을 동시에 두 번 취소하지 못하게 주문 줄을 비관적 락(2초 대기)으로 읽는다. 주문됨 상태가 아니면 409 `ORDER_NOT_CANCELABLE`로 거절한다.

## 3. 대안과 선택 이유

### 의존 방향

| 대안 | 장점 | 판단 |
| --- | --- | --- |
| **A. 쓰는 쪽(주문)이 포트를 소유** | 의존이 한 방향이다. 주문의 취소 사실을 결제·알림도 같은 이벤트로 받을 수 있다 | **선택.** 이미 머지한 #84의 타입을 옮겨야 하지만 동작은 바뀌지 않는다. |
| B. 재고가 "예약 해제 요청" 메시지를 소유 | 새 의존이 생기지 않는다 | 이벤트가 아니라 비동기 명령이 된다. 주문 모듈 자신의 "취소됨" 이벤트가 없어서, 결제 환불이나 알림이 붙을 때 메시지를 하나씩 더 만들어야 한다. |
| C. 이벤트 없이 `release()`를 직접 호출 | 순환이 없고 가장 단순하다 | 해제가 취소 트랜잭션에 묶이고, 취소를 알아야 하는 모듈이 늘 때마다 주문 서비스를 고쳐야 한다. 이 단계의 목표(Modulith 이벤트와 발행 기록)도 사라진다. |

A는 알려진 설계 원칙과 같은 방향이다.

- **Spring Modulith 문서의 예제:** 주문 관리가 재고 관리를 직접 부르던 코드를, 주문이 `OrderCompleted`를 발행하고 재고가 받는 구조로 바꾼다. 재고가 주문을 알고 주문은 재고를 모른다. 다만 문서 예제에는 즉시 답이 필요한 예약 호출이 없다. 그 동기 호출을 순환 없이 남기는 방법이 쓰는 쪽 소유의 포트다.
- **의존 역전 원칙(DIP)과 Separated Interface(Fowler, PoEAA):** 인터페이스를 쓰는 쪽 패키지에 두고 구현은 다른 패키지에 둔다.
- **헥사고날 아키텍처의 driven port:** 바깥 기능이 필요한 코어가 포트를 소유한다.

MSA에서는 주문 서비스가 재고 API를 부르고 재고 서비스가 주문 이벤트를 구독하는, 서로를 아는 구조가 흔하다. 서비스가 HTTP와 메시지로만 이어져 코드 수준의 순환 검사가 없기 때문이다. 모듈러 모놀리스는 이를 순환으로 막으므로 방향을 하나로 정한다.

### 중복 전달 대비

| 대안 | 판단 |
| --- | --- |
| **주문별 예약 기록과 상태** | **선택.** 해제할 대상과 수량을 재고 모듈이 스스로 안다. 이벤트는 주문 ID만 담으면 되고, 결제 단계의 예약 확정(#20)도 같은 기록 위에 쌓을 수 있다. |
| 처리한 이벤트 ID 기록 | 이벤트마다 처리 여부만 남긴다. 무엇을 해제했는지는 여전히 이벤트에 담아야 하고, 같은 주문을 다른 경로(만료 등)로 해제할 때 중복을 막지 못한다. |
| 중복을 허용 | 같은 이벤트가 다시 오면 재고가 늘어나 초과 판매로 이어진다. 아래 검증에서 재현했다. |

## 4. 트레이드오프

- **의존 방향이 규칙이 된다:** 주문이 중심이고 다른 모듈이 주문을 의존한다. 결제 모듈도 주문이 정한 인터페이스로 결과를 알려야 하며, 주문이 결제 이벤트를 구독하면 순환이 다시 생긴다.
- **해제가 늦을 수 있다:** 취소 응답 시점에는 재고가 아직 돌아오지 않았을 수 있다. 리스너가 실패하면 다시 제출할 때까지 재고가 묶인다.
- **실패한 기록을 다시 제출하는 주체가 아직 없다:** 지금은 `IncompleteEventPublications`를 직접 호출해야 한다. 주기적 재제출이나 운영 알림은 정하지 않았다.
- **저장이 늘었다:** 예약할 때 상품마다 `reservation` 행이, 취소할 때 `event_publication` 행이 하나씩 생긴다. 완료된 발행 기록의 정리 정책은 정하지 않았다.

## 5. 검증 결과와 한계

환경: Windows 11, Docker(Testcontainers) PostgreSQL 18.6, Spring Boot 4.1.2, Spring Modulith 2.1.2.

| 확인한 것 | 결과 |
| --- | --- |
| 포트를 옮기기 전 `OrderCanceled` 리스너 추가 | `ModularityTests` 실패 (`inventory -> order -> inventory` 순환) |
| 포트를 주문 모듈로 옮긴 뒤 | `ModularityTests` 통과 |
| 같은 주문을 동시에 10번 취소 | 주문 줄 락 없이 10건 모두 성공, 락을 건 뒤 1건만 성공 (`OrderCancellationConcurrencyTest`) |
| 재고 3개를 예약한 주문 취소 | 재고 7 → 10, 발행 기록 `COMPLETED` |
| 해제 중 재고 줄이 없어 실패 | 발행 기록 `FAILED`, 재고 등록 후 다시 제출하면 `COMPLETED`이고 재고 3 |
| 완료된 이벤트를 다시 전달 (기록을 `FAILED`로 바꿔 재제출) | 예약 기록 전: 재고 10 → 13 (두 번 해제). 예약 기록 후: 10 그대로 |
| 동시 예약 100건(재고 10) | 10건 성공, 예약 기록도 10행 |

검증하지 않은 것:

- 같은 이벤트가 **동시에** 두 번 처리되는 경우. 예약 기록을 잠가 읽으므로 늦은 쪽은 기다린 뒤 예약됨 기록을 찾지 못한다고 판단했지만(PostgreSQL READ COMMITTED의 조건 재확인), 테스트로 재현하지 않았다.
- 프로세스가 리스너 커밋과 발행 완료 표시 사이에 멈추는 실제 상황. 기록 상태를 바꿔 재제출하는 방식으로 흉내만 냈다.
- 이벤트 처리 지연과 처리량, 발행 기록 테이블이 커졌을 때의 영향.

## 6. 재검토 조건

- **흐름 조율 모듈:** 결제·만료·환불이 붙어 주문 모듈이 여러 모듈의 순서와 보상 처리를 떠안게 되면, 주문·재고·결제 위에 조율 모듈을 두고 세 모듈이 서로 모르게 하는 구조를 검토한다.
- **재제출 자동화:** 실패한 발행 기록이 운영 중 실제로 쌓이면 주기적 재제출과 알림을 정한다.
- **외부 메시지 브로커:** 다른 서비스로 이벤트를 내보내야 하면 Modulith의 이벤트 외부화(Kafka 등)를 검토한다.

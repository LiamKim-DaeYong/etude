# ADR-0005: 중소 제조사용 멀티테넌트 업무 시스템으로 방향 전환

| 항목 | 내용 |
| --- | --- |
| 상태 | 채택 |
| 결정일 | 2026-11-09 |
| 적용 범위 | 서비스의 대상 사용자, 모듈 구성, 개발 순서, 운영 비용과 보안 원칙 |
| 구현 상태 | 구현 전. 기존 상품·주문·재고 모듈에 테넌트 개념이 아직 없다 |
| 검증 상태 | 검증 전. 실제 사용 여부와 운영 비용은 확인하지 않았다 |

## 요약

- **결정:** 쇼핑몰 한 곳을 만드는 대신, **여러 중소 제조사가 함께 쓰는 업무 시스템과 홈페이지**를 만든다. 흩어져 있던 업무(주문, 재고, 생산, 홈페이지)를 한 서비스에 모은다.
- **구성:** 홈페이지는 업무 데이터를 그대로 보여 준다. 업무의 중심은 직접 만들고, 이미 잘 되어 있는 외부 서비스(세금계산서, 택배, 결제, 알림)는 연결한다. 쇼핑몰은 모듈 하나가 된다.
- **순서:** 한 번에 다 만들지 않는다. 실제 제조사 한 곳이 쓰는 흐름(테넌트, 상품 → 홈페이지, 주문 → 재고)부터 만들고 하나씩 넓힌다.
- **원칙:** 운영 구성은 앱 하나와 PostgreSQL 하나로 시작한다. 위험한 기능은 검증된 곳에 맡기고, 테넌트 데이터 격리는 두 겹으로 막는다.

## 1. 배경

Etude는 지금까지 주문·재고·결제를 갖춘 쇼핑몰 하나를 가정하고 동시 주문, 모듈 경계, 이벤트 같은 설계 문제를 다뤘다(ADR-0003, ADR-0004).

중소 제조사는 업무를 여러 곳에 나눠 관리하는 경우가 많다.

- 주문은 전화·팩스·메신저로 받아 엑셀에 옮긴다.
- 재고와 생산 현황은 담당자의 엑셀이나 기억에 있다.
- 홈페이지는 따로 만든 소개 페이지라 상품 정보가 업무 데이터와 따로 논다.
- 세금계산서, 택배, 입금 확인은 각자의 사이트에서 따로 처리한다.

WMS(창고 관리)와 MES(생산 관리)는 대기업용은 많지만, 소규모 제조사가 바로 쓰기에는 크고 비싸다. 이 흩어진 업무를 한곳에서 쉽게 쓰게 하는 것을 서비스의 목표로 삼는다.

## 2. 결정

### 2.1 대상과 사용자

여러 제조사가 서비스 하나를 함께 쓴다. 서비스를 함께 쓰는 회사 하나를 **테넌트**라 한다. 각 테넌트는 자기 데이터만 본다.

| 사용자 | 쓰는 곳 | 예 |
| --- | --- | --- |
| 플랫폼 운영자 | 운영 화면 | 테넌트 가입, 모듈 관리 |
| 테넌트 직원 | 업무 화면 | 상품 등록, 주문 등록, 재고 확인 |
| 테넌트의 고객(거래처, 방문자) | 테넌트 홈페이지 | 상품 보기, 문의, 주문 |

### 2.2 모듈 구성

```
테넌트 홈페이지   site(소개·문의), shop(온라인 주문), payment
        │ 같은 데이터를 보여 준다
업무 시스템       catalog(상품), order(주문), inventory(재고), production(생산), shipment(출고)
        │
플랫폼            tenant(회사·직원·권한), subscription(모듈 사용)
        │
연결              세금계산서, 택배, 결제, 알림 같은 외부 서비스
```

- **홈페이지는 업무 데이터를 보여 준다:** 직원이 업무 화면에서 상품을 등록하면 홈페이지에 나타나고, 홈페이지로 들어온 주문은 업무 화면에 나타난다. 별도의 홈페이지 콘텐츠를 두 번 관리하지 않는다.
- **중심은 직접 만들고 주변은 연결한다:** 상품, 주문, 재고, 생산, 출고는 테넌트마다 엑셀로 관리하던 것이라 직접 만든다. 세금계산서, 택배, 결제, 알림은 이미 있는 서비스를 외부 API로 연결한다.
- **모듈 단위로 켜고 끈다:** 테넌트는 필요한 모듈만 쓴다. 처음에는 테넌트별 모듈 사용 설정까지만 만들고, 요금 청구는 나중에 정한다.

### 2.3 개발 순서

| 단계 | 내용 |
| --- | --- |
| 1. 테넌트 기반 | 회사, 직원 계정, 모든 업무 데이터의 테넌트 구분. 기존 모듈도 바꾼다 |
| 2. 홈페이지 | 테넌트 소개, 상품 목록, 문의 |
| 3. 주문·재고·출고 | 직원이 전화·팩스 주문을 등록하고, 재고 예약부터 출고까지 |
| 4. 생산 | 작업 지시, 생산 실적, 재고 입고 |
| 5. 온라인 주문·결제 | 쇼핑몰 모듈 |
| 6. 구독 | 모듈 사용 관리, 요금 |

1~3단계가 첫 버전이다. 실제 제조사 한 곳이 이 흐름을 쓰는지 확인한 뒤 다음 단계로 넘어간다. 제조사의 주문은 소비자보다 거래처(회사)에서 전화·팩스로 오는 경우가 많다고 보고 직원의 주문 등록(3단계)을 온라인 주문(5단계)보다 앞에 둔다. 이 가정은 첫 사용자에게서 확인한다.

### 2.4 운영 비용

- 운영 구성은 **앱 하나(모듈러 모놀리스)와 PostgreSQL 하나**로 시작한다.
- 메시지 브로커, 캐시 서버, 컨테이너 오케스트레이션은 측정으로 필요를 확인하기 전에는 운영 구성에 넣지 않는다. 이 기술을 다루는 실험은 로컬과 테스트 환경에서 한다.
- 홈페이지는 읽기가 대부분이므로 CDN 캐시를 앞에 둔다.
- 실제 월 비용은 배포 단계에서 업체별로 확인해 기록한다.

### 2.5 보안

위험이 큰 기능은 직접 만들지 않고 검증된 곳에 맡긴다. 이 서비스만 막을 수 있는 위험은 두 겹으로 막는다.

| 위험 | 원칙 |
| --- | --- |
| 카드 정보 유출 | 카드 정보를 저장하지 않는다. 결제는 결제대행사(PG)에 맡긴다 |
| 계정 탈취 | 인증을 직접 구현하지 않고 Spring Security의 검증된 방식을 쓴다 |
| 개인정보 | 업무에 꼭 필요한 항목만 받는다 |
| **다른 테넌트의 데이터 노출** | **애플리케이션 코드와 데이터베이스 양쪽에서 막는다.** 방식은 별도 ADR로 정한다 |

## 3. 대안과 선택 이유

| 대안 | 판단 |
| --- | --- |
| A. 쇼핑몰 한 곳을 계속 만든다 | 동시성 문제를 다루기 쉽다. 다만 흔한 주제이고 실제 사용자가 없다. |
| **B. 멀티테넌트 업무 시스템으로 바꾼다** | **선택.** 상품·주문·재고는 두 방향 모두의 중심이라 지금 코드가 이어진다. 실제 사용자를 둘 수 있고, 데이터 격리·외부 연동처럼 쇼핑몰 한 곳에서는 생기지 않는 문제를 다루게 된다. |
| C. 쇼핑몰을 끝낸 뒤 별도 프로젝트로 시작한다 | 기능이 쌓인 뒤에 테넌트를 넣으면 고칠 곳이 훨씬 많다. 기능이 적은 지금 바꾸는 편이 싸다. |

## 4. 트레이드오프

- **동시성 문제가 저절로 생기지 않는다:** 테넌트 하나는 사용자가 적다. 요청은 테넌트가 많이 모일 때와 홈페이지 조회에서 늘어난다. 테넌트 하나의 무거운 작업이 다른 테넌트를 느리게 하는 문제(noisy neighbor)가 새로 생긴다.
- **범위가 커지기 쉽다:** 홈페이지, 업무 시스템, 외부 연동, 구독이 모두 후보다. 첫 버전을 1~3단계로 묶고, 다음 단계는 실제 사용을 확인한 뒤 넘어간다.
- **기존 모듈을 바꿔야 한다:** 상품·주문·재고의 모든 데이터와 조회에 테넌트 구분이 들어간다. 마이그레이션과 API 변경이 따른다.
- **테넌트마다 업무가 다르다:** 업종마다 생산 단위와 공정이 다르다. 설정으로 처리할 차이와 코드로 처리할 차이를 나눠야 한다. 첫 버전은 한 업종에 맞추고, 두 번째 업종이 생길 때 나눈다.

## 5. 열린 질문

이 ADR에서 정하지 않고, 해당 단계에서 정한다.

- **테넌트 데이터 격리 방식:** 테이블 공유와 테넌트 ID, 테넌트별 스키마, 테넌트별 데이터베이스 중 무엇을 쓸지. 데이터베이스 수준의 두 번째 방어선을 어떻게 둘지. 다음 ADR에서 정한다.
- **테넌트 식별:** 요청이 어느 테넌트의 것인지 무엇으로 알지(로그인한 직원 계정, 홈페이지 주소 등).
- **API 구분:** 지금의 고객 API(`/api/v1`)와 관리자 API(`/admin/v1`)를 테넌트의 고객, 테넌트 직원, 플랫폼 운영자에 어떻게 나눌지.
- **상품과 제품:** 지금은 용어집의 상품(`Product`)을 그대로 쓴다. 제조사는 직접 만든 것(제품)과 사서 파는 것(상품)을 구분하기도 하므로, 생산 단계에서 이 구분이 필요한지 정한다.
- **업무 범위:** 견적, 거래처 관리, 매출 집계처럼 첫 사용자가 실제로 필요로 하는 업무가 무엇인지.

## 6. 재검토 조건

- 첫 사용자가 1~3단계를 실제로 쓰지 않으면 대상 업무와 순서를 다시 정한다.
- 운영 비용이나 처리량이 앱 하나와 PostgreSQL 하나로 감당되지 않는다는 측정이 나오면 구성을 바꾼다.
- 테넌트 하나의 요구가 다른 테넌트와 크게 달라 설정으로 처리할 수 없으면 업종별 구성을 검토한다.

# ADR-0006: 테넌트 데이터 격리와 식별

| 항목 | 내용 |
| --- | --- |
| 상태 | 제안 |
| 결정일 | — |
| 적용 범위 | 테넌트에 속한 모든 업무 데이터의 저장·조회, 데이터베이스 연결 권한, 요청의 테넌트 식별 |
| 구현 상태 | 구현 전(#105) |
| 검증 상태 | Hibernate `@TenantId`와 RLS의 동작을 실험 테스트로 확인(4절). 애플리케이션에 적용한 통합 검증은 구현 단계에서 한다 |

## 요약

- **결정:** 모든 테넌트가 테이블을 함께 쓰고, 테넌트에 속한 행마다 `tenant_id`를 둔다.
- **두 겹 방어:** 애플리케이션은 Hibernate `@TenantId`로 테넌트 ID를 자동으로 채우고 조회를 거른다. 데이터베이스는 PostgreSQL 행 수준 보안(Row-Level Security, RLS)으로 현재 테넌트의 행만 보여 준다. 한쪽이 실수해도 다른 쪽이 막는다.
- **식별:** 테넌트 ID는 서버가 확인한 것에서만 얻는다. 직원은 로그인한 계정의 소속 테넌트, 홈페이지 방문자는 접속한 주소에 연결된 테넌트다. 클라이언트가 보낸 테넌트 ID는 믿지 않는다.
- **확장:** 테넌트 하나를 나중에 별도 데이터베이스로 옮길 수 있도록 지금부터 세 가지 조건을 지킨다.

## 1. 배경

ADR-0005로 여러 제조사가 서비스 하나를 함께 쓰게 됐다. 다른 테넌트의 데이터가 보이는 것이 이 서비스에서 가장 큰 사고이고, 애플리케이션 코드와 데이터베이스 양쪽에서 막기로 했다.

고려한 조건은 다음과 같다.

- **비용:** 운영 구성은 앱 하나와 PostgreSQL 하나로 시작한다(ADR-0005).
- **테넌트 규모:** 소규모 제조사가 많이 모인다. 테넌트 하나의 데이터는 작다.
- **실수 가능성:** 조회마다 테넌트 조건을 직접 붙이면 언젠가 빠뜨린다.

## 2. 결정

### 2.1 격리 방식: 테이블 공유와 `tenant_id`

| 대안 | 장점 | 판단 |
| --- | --- | --- |
| **A. 테이블 공유, 행마다 `tenant_id`** | 비용이 가장 낮다. 테넌트가 늘어도 스키마와 마이그레이션은 하나다 | **선택.** 조건을 빠뜨리는 위험은 두 겹 방어로 막는다 |
| B. 테넌트별 스키마 | 격리가 더 강하다 | 테넌트 수만큼 마이그레이션을 돌려야 한다. 테넌트가 많으면 카탈로그와 커넥션 관리가 무거워진다 |
| C. 테넌트별 데이터베이스 | 격리가 가장 강하다 | 비용이 테넌트 수에 비례한다. 소규모 테넌트가 많은 서비스에 맞지 않는다 |

### 2.2 첫 번째 방어선: 애플리케이션

- 테넌트에 속한 엔티티는 공통 클래스를 상속한다. 공통 클래스는 `BaseEntity`를 상속하고 Hibernate `@TenantId` 필드 `tenantId`를 가진다. `Tenant` 자체처럼 테넌트에 속하지 않는 엔티티는 `BaseEntity`를 그대로 상속한다.
- `@TenantId` 필드는 엔티티를 처음 저장할 때 현재 테넌트 ID로 자동으로 채워지고, 애플리케이션이 직접 값을 넣을 수 없다(Hibernate javadoc).
- 현재 테넌트는 Hibernate `CurrentTenantIdentifierResolver` 하나가 알려 준다. 모듈 코드는 테넌트 ID를 직접 다루지 않는다.

### 2.3 두 번째 방어선: 데이터베이스 행 수준 보안

- 테넌트에 속한 모든 테이블에 RLS를 켜고, `tenant_id`가 현재 테넌트와 같은 행만 읽고(`USING`) 쓰게(`WITH CHECK`) 하는 정책을 둔다.
- 정책은 `tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid`로 쓴다(4절).
- 현재 테넌트는 트랜잭션마다 `set_config('app.tenant_id', ?, true)`로 알린다. 세 번째 인자 `true`는 트랜잭션이 끝나면 값이 사라지게 해서, 커넥션 풀이 연결을 다른 요청에 넘겨도 값이 남지 않는다.
- 값이 없으면 어떤 행도 보이지 않게 한다. 테넌트를 모르는 요청은 실패해야 한다.
- 테이블 소유자와 슈퍼유저는 RLS를 우회한다. 애플리케이션은 테이블 소유자가 아니고 `BYPASSRLS` 권한이 없는 역할로 접속한다. 마이그레이션(Flyway)은 소유자 역할로 따로 접속한다.

### 2.4 테넌트 식별

요청이 어느 테넌트의 것인지는 **서버가 확인한 정보에서만** 정한다. 요청 헤더나 본문의 테넌트 ID를 믿으면, 값을 바꾸는 것만으로 다른 테넌트의 데이터에 접근할 수 있다.

| 사용자 | 식별 근거 | 허용 범위 |
| --- | --- | --- |
| 테넌트 직원 | 서버 세션에 저장된 로그인 계정의 소속 테넌트 | 소속 테넌트의 업무 데이터 |
| 테넌트 홈페이지 방문자 | 요청이 들어온 주소(도메인)와 테넌트를 연결한 서버의 기록 | 그 테넌트의 공개 데이터(상품 목록, 문의 작성 등) |
| 플랫폼 운영자 | 테넌트에 속하지 않는다 | 별도 역할과 경로. 아래 열린 질문 |

- 직원 계정 하나는 테넌트 하나에만 속한다. 소규모 제조사에서 한 사람이 여러 테넌트를 쓰는 경우는 드물다고 보고 단순하게 시작한다.
- 식별한 테넌트는 2.2의 `CurrentTenantIdentifierResolver`와 2.3의 `set_config`에 같은 값으로 전달한다. 두 방어선이 서로 다른 테넌트를 보는 일이 없어야 한다.
- 테넌트를 식별하지 못한 요청은 테넌트 데이터에 접근하지 못한다.

### 2.5 나중에 테넌트를 옮기기 위한 조건

큰 테넌트나 데이터 분리를 요구하는 테넌트만 별도 데이터베이스로 옮기는 혼합 구성을 열어 둔다. 이를 위해 지금부터 지킨다.

1. **테넌트에 속한 모든 테이블에 `tenant_id`를 둔다.** 주문 항목처럼 다른 행에 딸린 테이블도 포함한다. `tenant_id` 하나로 테넌트의 데이터를 모두 뽑을 수 있어야 한다.
2. **테넌트 사이에 겹치지 않는 ID를 쓴다.** UUIDv7(ADR-0001)이므로 데이터를 옮겨도 ID가 충돌하지 않는다.
3. **현재 테넌트는 한 곳에서 정한다.** 나중에 그곳에서 테넌트별 데이터베이스를 고를 수 있다.

## 3. 트레이드오프

- **모든 테이블과 쿼리에 `tenant_id`가 늘어난다:** 저장 공간과 인덱스가 커진다. 테넌트별 조회가 많으므로 주요 인덱스는 `tenant_id`로 시작해야 할 수 있다.
- **트랜잭션마다 SQL이 하나 늘어난다:** `set_config` 호출이다. 영향은 측정하지 않았다.
- **데이터베이스 역할이 둘이 된다:** 애플리케이션 역할과 마이그레이션 역할을 로컬·테스트·운영 설정에 모두 둬야 한다.
- **테넌트 정보가 요청 밖으로 전달되지 않는다:** 비동기 이벤트 리스너(ADR-0004)는 다른 스레드와 트랜잭션에서 실행된다. 리스너에도 테넌트를 알려 주지 않으면 RLS가 모든 행을 막는다.

## 4. 구현 전 확인 결과

`TenantIsolationExperimentTest`(테스트 소스 `experiment.tenant`)로 확인했다. Spring 컨텍스트 없이 순수 Hibernate와 JDBC로 실행한다.

환경: Windows 11, Docker(Testcontainers) PostgreSQL 18.6, Hibernate ORM 7.4.13, HikariCP 7.0.2(풀 크기 1).

| 확인한 것 | 결과 |
| --- | --- |
| `@TenantId` 엔티티 저장 | 현재 테넌트 ID가 자동으로 채워진다 |
| 애플리케이션이 다른 테넌트 ID를 넣고 저장 | `PropertyValueException`(assigned tenant id differs from current tenant id)으로 거절 |
| HQL 조회 | `where tenantId = ?`가 자동으로 붙어 현재 테넌트 행만 나온다 |
| 다른 테넌트 행을 `find(id)` | SQL에 `id = ? and tenantId = ?`가 붙고 `null`을 돌려준다 |
| native query | **걸러지지 않는다.** 다른 테넌트 행까지 센다. 두 번째 방어선이 필요한 근거다 |
| 현재 테넌트 없이 세션 사용 | `HibernateException`(no tenant identifier specified)으로 실패한다 |
| 애플리케이션 역할로 조회 (RLS) | 현재 테넌트 행만 나온다 |
| `FOR NO KEY UPDATE` 조회 (RLS) | 현재 테넌트 행만 잠그고 돌려준다 |
| 다른 테넌트 행 삽입 (RLS) | `new row violates row-level security policy`로 거절 |
| `set_config(..., true)` 뒤 같은 풀 연결의 다음 트랜잭션 | 값이 `NULL`이 아니라 **빈 문자열**로 남고, 행은 보이지 않는다 |
| 위 상황에서 `current_setting(...)::uuid`를 그대로 쓴 정책 | `invalid input syntax for type uuid: ""`로 쿼리가 실패한다. 정책은 `nullif(current_setting('app.tenant_id', true), '')::uuid`로 쓴다 |
| 슈퍼유저로 조회 | 정책을 우회해 모든 행이 보인다. 애플리케이션 역할을 따로 둬야 하는 근거다 |

아직 확인하지 않은 것:

- Spring 트랜잭션 안에서 `set_config`를 부르는 위치와 `CurrentTenantIdentifierResolver`를 같은 값으로 묶는 방법. 구현 단계에서 통합 테스트로 확인한다.
- 트랜잭션마다 늘어나는 `set_config` 호출과 RLS 정책의 성능 비용.

## 5. 열린 질문

- **여러 테넌트에 속한 사용자:** 한 사람이 여러 테넌트를 쓰는 요구가 실제로 생기면 계정과 소속을 나누고 테넌트 전환을 정한다.
- **홈페이지 주소:** 서비스가 주는 하위 도메인과 테넌트가 가진 도메인 중 무엇을 지원할지, 테넌트가 가진 도메인의 소유를 어떻게 확인할지.
- **이벤트 리스너의 테넌트:** 이벤트에 테넌트 ID를 담을지, 발행 시점의 테넌트를 리스너에 넘길지.
- **테넌트 간 조회:** 플랫폼 운영자가 여러 테넌트를 보는 기능을 어떤 역할과 경로로 허용할지.
- **테넌트에 속하지 않는 데이터:** 이벤트 발행 기록(`event_publication`) 같은 공통 테이블의 범위.

## 6. 재검토 조건

- 테넌트 하나의 데이터나 요청이 다른 테넌트의 성능에 영향을 준다는 측정이 나오면 그 테넌트를 별도 데이터베이스로 옮긴다.
- RLS의 성능 비용이 측정으로 문제가 되면 정책과 인덱스를 다시 정한다.

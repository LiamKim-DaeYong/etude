# ADR-0007: 모듈 층과 의존 방향

| 항목 | 내용 |
| --- | --- |
| 상태 | 제안 |
| 결정일 | — |
| 적용 범위 | 백엔드 모듈의 층 구분, 모듈 사이 의존 규칙, 판매 채널과 주문의 관계 |
| 구현 상태 | 지금 모듈(`shared`, `platform`, `catalog`, `order`, `inventory`)의 의존 선언은 이 규칙을 따른다. 나머지 모듈은 구현 전 |
| 검증 상태 | `ModularityTests`가 지금 모듈의 의존 선언을 검사한다. 새 층의 모듈은 아직 없다 |

## 요약

- **목표:** 여러 판매 채널의 주문을 모으는 서비스(예: 사방넷)보다 체계적이고 쓰기 쉬운 서비스를 만든다. 주문 수집에서 끝나지 않고 물류와 제조까지 한 데이터로 잇고, 테넌트의 홈페이지까지 갖춘다.
- **층:** 공통 → 인프라 → 인증/인가 → 서비스 공통 → 서비스(쇼핑몰, 주문수집, 물류, 제조). 위층은 아래층을 쓸 수 있고 아래층은 위층을 모른다.
- **서비스 사이:** 직접 부르지 않고 이벤트로 알린다. 즉시 답이 필요하면 쓰는 쪽이 인터페이스를 정한다(ADR-0004). 순환은 허용하지 않는다.
- **패키지:** 층마다 패키지를 중첩하지 않는다. 모듈은 `dev.etude` 바로 아래에 두고, 층은 이 문서와 각 모듈의 `allowedDependencies`로 표현한다.
- **주문:** 주문수집(OMS)이 모든 주문이 모이는 곳이다. 우리 쇼핑몰도 판매 채널 하나다.

## 1. 배경

ADR-0005로 여러 중소 제조사가 함께 쓰는 업무 시스템과 홈페이지로 방향을 바꿨다. 다중 채널 주문 수집 서비스는 이미 있지만, 판매 채널 쪽 업무에 집중되어 있고 물류·생산과는 따로 논다. 이 서비스는 주문 수집, 물류, 제조, 홈페이지를 한 데이터 위에 두고 쉽게 쓰게 하는 것을 목표로 한다.

기능이 늘어나도 모듈이 서로 얽히지 않아야 하고, 테넌트가 구독하지 않은 서비스가 빠져도 나머지가 동작해야 한다. 그래서 모듈을 층으로 나누고 의존 방향을 정한다.

## 2. 결정

### 2.1 층

| 층 | 담는 것 | 모듈 (예정 포함) |
| --- | --- | --- |
| 서비스 | 구독 단위의 기능 | 쇼핑몰(`shop`), 주문수집(`order`, `inventory`), 물류, 제조 |
| 서비스 공통 | 여러 서비스가 함께 쓰는 업무 데이터 | 상품(`catalog`), 거래처 |
| 인증/인가 | 누가 어느 테넌트로 무엇을 할 수 있는가 | 테넌트(`tenant`: 회사·직원), 로그인·권한 |
| 인프라 | 모든 요청에 걸치는 기술 장치 | `platform` (오류 처리, 시간, 현재 테넌트 장치) |
| 공통 | 모든 모듈이 같은 뜻으로 쓰는 값과 영속성 기반 | `shared` (`Money`, `BaseEntity`, 테넌트용 공통 엔티티) |

- 지금의 `inventory`는 상품별 판매 가능 수량이므로 주문수집에 속한다. 창고·위치 단위의 실물 재고는 물류에 따로 둔다(ADR-0005 열린 질문).
- 물류와 제조의 모듈 이름과 나누는 단위는 해당 단계에서 정한다.

### 2.2 의존 규칙

1. 위층 모듈은 아래층 모듈을 쓸 수 있다. 아래층은 위층을 모른다. 예: 상품은 쇼핑몰과 물류를 모른다.
2. 같은 층의 서비스끼리는 이벤트로 알린다. 예: 제조가 생산을 마치면 이벤트를 발행하고 물류가 받는다.
3. 서비스가 다른 서비스의 즉시 답을 필요로 하면, 쓰는 쪽이 인터페이스를 정하고 상대가 구현한다(ADR-0004). 의존은 한 방향이다.
4. 순환 의존은 허용하지 않는다.
5. 아래층이 위층의 정보를 필요로 하면(예: 인프라가 홈페이지 주소로 테넌트를 찾을 때) 아래층이 인터페이스를 정하고 위층이 구현한다.

### 2.3 패키지와 검사

- 모듈은 지금처럼 `dev.etude.<module>`에 둔다. 층마다 `dev.etude.service.order`처럼 중첩하면 Spring Modulith가 상위 패키지 하나를 모듈 하나로 보아, 그 안의 모듈 사이 경계 검사가 사라진다.
- 각 모듈의 `ModuleMetadata`에 `allowedDependencies`로 쓸 수 있는 모듈을 선언한다. 2.2를 어기면 `ModularityTests`가 실패한다.
- 모듈이 많아져 한눈에 보기 어려워지면 Spring Modulith의 중첩 모듈을 다시 검토한다.

### 2.4 테넌트의 위치

ADR-0006의 테넌트는 성격에 따라 세 곳에 나눠 둔다.

| 무엇 | 층 | 위치 |
| --- | --- | --- |
| 회사 자체(이름, 나중에 직원·홈페이지 주소·구독) | 인증/인가 | `tenant` 모듈 |
| 행이 어느 테넌트 것인지의 표시(`tenantId`) | 공통 | `shared`의 테넌트용 공통 엔티티 |
| 현재 요청의 테넌트를 정하고 Hibernate와 데이터베이스에 알리는 장치 | 인프라 | `platform` |

상품·주문·재고 모듈은 `tenant` 모듈에 의존하지 않는다. 테넌트 ID는 값으로만 다루고, 테넌트 구분은 `shared`와 `platform`이 처리한다.

### 2.5 주문과 판매 채널

```
외부 마켓(스마트스토어, 쿠팡 등) ─┐
우리 쇼핑몰(shop)                ─┼─→ 주문수집(order) ─→ 물류 → 출고
전화·팩스(직원 등록)             ─┘
```

- 주문수집이 모든 주문이 모이는 곳이다. 우리 쇼핑몰의 주문도 다른 판매 채널과 같은 방식으로 들어온다.
- 첫 버전은 직원이 전화·팩스 주문을 등록하는 경로만 만든다(ADR-0005의 3단계).
- 주문에는 처음부터 어느 판매 채널에서 왔는지를 남긴다. 외부 마켓 연동을 붙일 때 주문 구조를 다시 바꾸지 않기 위해서다.
- 외부 마켓 연동은 주문을 가져오는 방향(주문 수집)과 내보내는 방향(상품 등록, 재고 수량, 송장 번호)이 모두 있다. 같은 주문을 두 번 수집하지 않도록 (판매 채널, 채널의 주문 번호)로 중복을 막는다. 연동 모듈의 위치와 방식은 해당 단계에서 정한다.

### 2.6 개발 방식: 슬라이스

모듈 하나를 깊이 만들지 않는다. 기능 하나가 필요한 모듈을 얇게 관통하도록 만들고(수직 슬라이스), 슬라이스마다 모듈 사이의 연결 지점을 찾아 함께 올린다.

- 슬라이스가 지나가는 모듈은 패키지와 `ModuleMetadata`만 먼저 만들고, 그 슬라이스에 필요한 만큼만 채운다.
- 경계가 아직 분명하지 않은 모듈(물류의 실물 재고, 제조)은 슬라이스가 닿을 때 만든다. 이름과 경계를 추측으로 정하지 않기 위해서다.
- 테넌트 기반(ADR-0006)은 모든 기능의 바닥이므로 첫 슬라이스에서 끝낸다.

| 슬라이스 | 흐름 | 지나가는 모듈 |
| --- | --- | --- |
| 1 | 랜딩 → 회원가입(회사 + 대표) → 대표 로그인 → 직원 등록 → 직원 로그인 → 상품 등록 | `tenant`, 인증, `catalog` |
| 2 | 홈페이지에서 그 회사의 상품 보기 | 홈페이지, `catalog` |
| 3 | 전화 주문 등록 → 재고 예약 → 출고 | `order`, `inventory`, 출고 |
| 4 | 생산 → 창고 입고 → 판매 가능 수량 증가 | 제조, 물류, `inventory` |

순서는 ADR-0005의 개발 순서를 따르고, 실제 사용에서 확인한 것에 따라 바꾼다.

## 3. 대안과 선택 이유

| 대안 | 판단 |
| --- | --- |
| **평평한 모듈 + 의존 선언으로 층 표현** | **선택.** 모듈 사이 경계 검사가 그대로 유지되고, 층 규칙도 `ModularityTests`로 검사된다. |
| 층별 패키지 중첩 (`dev.etude.service.order`) | 폴더에서 층이 보인다. 다만 Modulith의 기본 탐지에서는 상위 패키지가 모듈 하나가 되어 경계 검사가 줄어든다. 중첩 모듈 설정을 따로 해야 한다. |
| 서비스(구독 단위)별 패키지 (`oms`, `wms`, `mes`) | 판매 단위가 그대로 보인다. 다만 상품·재고처럼 여러 서비스가 함께 쓰는 데이터의 자리가 애매하고, 구독 묶음이 바뀌면 패키지를 옮겨야 한다. 실물 재고가 들어오는 단계에서 다시 검토한다(ADR-0005). |

## 4. 트레이드오프

- **층이 폴더에 보이지 않는다:** 어느 모듈이 어느 층인지는 이 문서와 의존 선언을 봐야 안다.
- **서비스 사이 이벤트는 결과가 늦게 반영된다:** 생산 완료가 물류에 바로 보이지 않을 수 있다. 즉시 답이 필요한 경우만 인터페이스 호출을 쓴다.
- **구독에 서비스 사이의 필요 관계가 생긴다:** 쇼핑몰 주문은 주문수집으로 들어가므로 쇼핑몰만 따로 구독할 수 없다. 구독 묶음을 정할 때 이 관계를 반영한다.

## 5. 재검토 조건

- 모듈이 많아져 의존 선언만으로 층을 파악하기 어려우면 중첩 모듈을 검토한다.
- 서비스 하나를 별도 배포 단위로 떼어 내야 하면, 그 서비스의 모듈과 이벤트 경계를 기준으로 나눈다.
